| ES8311 sample-rate sweep 8 kHz - 48 kHz (HW-019) | **PENDING - not hardware-verified** | none yet; `CONFIG_APP_AUDIO_RATE_SWEEP` produces it | The 2026-07-12 driver rewrite widened the supported rates from 16 kHz alone to 8 kHz - 48 kHz. The argument is that the codec's master clock is derived from BCLK, so it is 256 * Fs at every rate and the divider chain is a pure ratio, which means one register set serves them all. That argument is corroborated by the ES8311 user guide's own clock table, by Linux `sound/soc/codecs/es8311.c` (identical REG02 = 0x18 / REG05 = 0x00 at every rate) and by `i2s_esp32.c` producing BCLK = 32 * Fs exactly, and it is pinned by the ztest, **but it is not measured on silicon yet**. Only 16 kHz is hardware-verified (HW-006 / HW-016d). `CONFIG_APP_AUDIO_RATE_SWEEP` reprograms I2S and the codec at each rate, reads the clock registers back over I2C and plays a tone while capturing it on the microphone. **8 kHz is the rate at risk**: both Espressif reference drivers special-case it (x4 instead of x8) claiming BCLK must be at least 512 kHz, which the datasheet does not state, which Linux contradicts, and which Espressif's own 11.025 kHz row (x8 at 352.8 kHz) contradicts. If it fails, `8000` is dropped from `es8311_rates[]` before the upstream submission. **What HW-019 will and will not prove.** Per rate it checks three independent things: the clock registers read back off the chip (which proves only that the driver wrote what it meant to); the frame clock **measured** by timing DMA blocks against the kernel cycle counter, which is not derived from the I2S clock (a mis-programmed divider shows up here and nowhere else); and that the ADC is alive with the amplifier off, since a codec whose clock tree failed to lock cannot run its modulator and returns zeros or a stuck constant. The acoustic loopback deliberately does NOT gate the verdict: TX and RX share the clock, so a common error cancels, and this speaker couples too weakly into this microphone for a threshold to mean anything. A green sweep is therefore **register + interface-timing + ADC-liveness** validation - not a proof of the codec's internal filters, OSR or analog bandwidth, which would need an external tone into the microphone and a measured recovered frequency. It also covers the **route transitions** on silicon (playback-only / capture-only / both, reading back 0x01/0x09/0x0A/0x0D/0x0E/0x12/0x14), because the rate loop only ever asks for PLAYBACK_CAPTURE and so writes not one of the power-down values the route fix is actually made of; until this runs they have only been checked against an emulator that cannot disagree with them. And it verifies that the sweep **restores** 16 kHz and hands back a working device, measured rather than assumed: the first version restored by calling `audio_init()`, which re-probes the codec, and `device_init()` returns `-EALREADY` on an already-initialized device - so it would have printed PASS for every rate and left audio dead |
